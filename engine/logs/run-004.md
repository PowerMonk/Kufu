- **Model**: `gemma4:e4b`
- **Context window**: `num_ctx = 8192`
- **Prompt**: `simple-prompt.md`

## What changed from run-003

This run delivered two interlocking pieces of infrastructure: a redesigned ledger that doesn't pretend Ollama calls stack, and a pluggable evaluator with three layers that output a single typed report.

### Phase 4 — Per-call utilization in the ledger

`engine/src/usage.ts` was refactored. The previous ledger conflated two different metrics:

- **Cumulative saturation** (`prev_sat% → new_sat%` based on `cum_in / num_ctx`) — read like the model was filling up across calls.
- **Per-call utilization** (this call's prompt / num_ctx) — the honest answer to "how full is this call's brain?".

The Ollama docs make clear that each chat request gets its own KV cache: `PredictServerVRAM` from the Ollama source computes `weights + 2 × layers × kv_heads × head_dim × context × 2 bytes`. Calls don't share KV. So we now surface **per-call** columns (`in%`, `out%`, `tot%`) and keep cumulative cost accounting in separate columns (`cum_in`, `cum_out`, `cum_total`). The ledger footer is a `cost_summary:` block instead of a one-line peak.

### Phase 5a — Eval contracts + runner scaffold

New directory `engine/src/eval/` with these files:

- `eval/contract.ts` — Zod schemas for `CheckResult`, `TaskCorrectnessResult`, `StructuralResult`, `CodeQualityResult`, `VisualResult` (stub), `Cost`, `EvalReport`. The union covers all four layers; layers are optional in `EvalReport` so we can ship incrementally.
- `eval/task.ts` — types for `TaskManifest`, `TaskRequirement`, `RequirementType`, `OutputKind`, `LayerName`. Manifests are pure JSON; the runner validates them at load.
- `eval/runner.ts` — orchestrator. `runEvaluation(manifest, output, cost)` walks the declared layers, merges results, computes `passed`. Cost comes from the existing `BenchmarkRecord` so we don't double-count tokens.

### Phase 5b — Layer 1 (task correctness) + Layer 2 (structural HTML)

**Layer 1** lives at `eval/layers/task.ts`. Uses `htmlparser2` and a tiny CSS-subset selector engine (`eval/selector.ts`). Supports `tag`, `.class`, `#id`, and comma-separated OR. Combinators (`>`, `+`, `~`) and attribute selectors are deliberately out of scope for now.

Requirement types implemented:

- `element` — selector matches at least one element.
- `count` — selector matches N times where `min <= N <= max`.
- `text` — substring of body text (case-insensitive, whitespace-normalized).
- `attr` — first matching element has attribute `= value`.
- `style` — **deferred to Layer 4** (would require a browser). Stub returns `pass: true` so manifests with style requirements don't break.

**Layer 2** lives at `eval/layers/structural.ts` + `eval/checks/html.ts`. 12 pure-string/parser checks:

1. `has_doctype`
2. `has_html_lang`
3. `has_title`
4. `has_meta_charset`
5. `has_viewport`
6. `images_have_alt`
7. `buttons_not_divs` (no `on*=...` on non-button elements)
8. `links_have_href`
9. `no_duplicate_ids`
10. `heading_hierarchy` (no level skipping)
11. `no_empty_elements` (whitespace-only div/p/span/section/article)
12. `no_inline_event_handlers`

A subset (`images_have_alt`, `buttons_not_divs`, `no_inline_event_handlers`, `has_html_lang`) is counted as **accessibility_issues** in the report so the JSON distinguishes a11y from generic HTML errors.

### Phase 5c — Layer 3 (code quality) + first task manifest

**Layer 3** at `eval/layers/quality.ts` + `eval/checks/general.ts`. At launch it computes:

- `loc` — non-blank, non-comment lines
- `file_count` — 1 (single-file output)
- `asset_count` — local `<img src>`, `<link href>`, `<script src>` (CDN excluded)
- `broken_imports` — 0 (stub; future: parse + check)
- `syntax_errors` — 1 if `htmlparser2` parseDocument throws (smoke test)
- `unused_symbols` — 0 (stub; meaningful when we add TS)

Honest scope: Layer 3 produces schema-correct numbers but most checks are placeholders. The shape is stable for Phase 6 leaderboards.

**First task manifest** at `engine/eval/tasks/landing-001.json`:

```json
{
  "task_id": "landing-001",
  "output_kind": "html",
  "requirements": [
    { "id": "hero_section", "type": "element", "selector": "header" },
    { "id": "roles_grid", "type": "count", "selector": "article, .role, .card, .role-card", "min": 3 },
    { "id": "has_footer", "type": "element", "selector": "footer" },
    { "id": "mentions_planner", "type": "text", "expected": "Planner" },
    { "id": "mentions_implementer", "type": "text", "expected": "Implementer" },
    { "id": "mentions_reviewer", "type": "text", "expected": "Reviewer" }
  ],
  "layers": ["task", "structural", "quality"]
}
```

Note the OR selector `article, .role, .card, .role-card` in `count` — the implementer picked `<article>` this time but our earlier variants sometimes used `.role-card`. A manifest that locks one selector is brittle when the model's HTML conventions shift. As we observe patterns we'll tighten selectors; for now lenient beats brittle.

### CLI integration

`engine/src/main.ts` parses `--task-manifest <path>`, resolves it, JSON-parses it, and threads it through `runPipeline` / `runSingle`. When unset, the evaluator is a no-op — backward compatible with run-003.

`engine/src/types.ts` gained optional `taskManifest?: TaskManifest` on `PipelineInputs` and `SingleInputs`. `pipeline.ts` and `single.ts` call a small `writeEval` helper after the benchmark report is written.

`htmlparser2@12.0.0` is the new dev dependency. ~10KB, no transitive bloat.

### What failed and why

**Pipeline 12/12** — all checks pass. The implementer's output starts directly with `<!DOCTYPE html>`, includes semantic landmarks (`<header>`, `<main>`, `<footer>`), uses no `<img>` tags (so `images_have_alt` trivially passes), and the heading hierarchy is clean.

**Single 10/12** — two failures:
- `has_doctype`: single mode wraps the file in a markdown fence (` ```html `) and adds prose preamble ("Here is the file..."). The structural checker sees the fence as the first non-whitespace, not `<!DOCTYPE>`. This is the exact "no system prompt" disadvantage documented in run-002 (`engine/logs/run-002.md:99-103`). The structural layer surfaced it deterministically.
- `heading_hierarchy`: h1 → h3 skip. Real bug in the generated HTML.

**Single-thinking 11/12** — one failure:
- `has_doctype`: same fence issue as plain single. Other 11 checks pass.

### Eval is doing its job

The interesting finding is that **single mode has been quietly failing structural HTML checks every run** — the run-002 and run-003 logs discussed this qualitatively ("the model wraps output in prose") but never had a number for it. Now we do:

- pipeline: 0/12 structural failures
- single:    2/12 structural failures
- single-thinking: 1/12 structural failure

That's exactly the kind of comparison the project needs. The pipeline's lead isn't just "the code looks cleaner" — it's "the code is structurally correct by 12 deterministic checks".

## What worked

1. **Per-call utilization is the right metric.** A reader can now see `in% 9.0 out% 28.7 tot% 37.7` and answer "this implementer call used ~38% of its context window". No more reading the cumulative column and incorrectly assuming the model is filling up across calls.
2. **EvalReport catches model output conventions deterministically.** Fences, heading skips, missing doctype — all flagged with structured fields, no manual review needed.
3. **`taskManifest` is purely additive.** When omitted, behavior is identical to run-003 (verified by re-reading `main.ts` and `pipeline.ts`). When present, `eval.json` lands in the same output dir.
4. **Selector engine's recursive walker.** The "find nested `<article>`" test (`engine/src/eval/eval.test.ts:73-92`) exercises the count walker end-to-end and passes — important because the implementer's output nests elements several levels deep.
5. **htmlparser2 stayed cheap.** No transitive deps pulled in. `bun test` runs in ~50ms for the eval test suite.

## What didn't work

1. **Single mode + markdown fence still defeats `has_doctype`.** The structural checker currently doesn't strip fences. Two options for next phase: (a) add a fence-stripping preprocess step, (b) leave it as a known weakness (single mode is documented as raw baseline). I'd lean toward (a) — it makes the comparison fair without giving single mode a system prompt.
2. **Heading hierarchy skips in single mode.** Two options: (a) loosen the check to "allow one skip", (b) keep strict and let single mode fail it. Strict is correct for "real" HTML; if a designer wants to allow skips, they can edit the check.
3. **Layer 4 stub.** Visual / runtime checks aren't built yet. The contract has a placeholder `VisualResult` schema that `runEvaluation` doesn't populate. Implementing it requires a headless browser (jsdom or Playwright).
4. **Cost numbers shifted slightly between run-003 and run-004 for the pipeline variant.** Tokens: run-003 had total=3739; run-004 has total=4524. Cause: a small prompt tweak in `simple-prompt.md` between runs (added "No JavaScript interactivity required." line — see commit history). Same model, same seed, slightly different prompt → different generation. Variance is on the prompt input, not the model.

## Implications for the project

### Eval makes the comparison real

Before this run, "single mode wraps output in prose" was a stylistic observation. After this run, it's `html_errors: 2, accessibility_issues: 0` and a `passed: false` flag. The pipeline's lead has a number now.

### Layered eval scales to future task types

The contract (`EvalReport`) treats layers as optional. Phase 6 can add new tasks — pricing card, refactor function, fix typo — and Layer 1 selectors + Layer 3 quality metrics adapt without changing existing code. To add a Rust task: drop a new `checks/rust.ts` file and the runner dispatch in `runner.ts:defaultLayers`. No changes to `pipeline.ts`, `single.ts`, `main.ts`, or any UI code.

### Determinism with eval

The evaluator is pure JS so it adds zero non-determinism. The seed flag still binds the LLM output (verified by prompt-shape match with run-003's ledger structure). Three reps at the same prompt should produce the same `eval.json`. We can verify this in run-005.

3. **Phase 6 (Eval suite)** — 5–10 task manifests in `engine/eval/tasks/`. Define a runner script that loops over tasks × variants × reps and emits `engine/eval/leaderboard.csv`.
