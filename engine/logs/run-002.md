# Run 002 — Schema improvements and first working pipeline

- **Date**: 2026-06-16
- **Model**: `gemma4:e4b`
- **Context window**: `num_ctx = 8192`
- **Prompt**: `simple-prompt.md`

## What changed from run-001

Two schema changes were applied before this run:

1. **Removed `id` field** from `PlannerTask` — the model was using it as a free-form label instead of a uuid.
2. **Added `task` field** with `min(20)` constraint — the model was filling it with single words like "UPDATE" instead of describing the change.

These changes were meant to force the planner to produce actionable instructions.

## Code quality analysis

### Pipeline output (run-002/implementer.txt)

**What it got right:**

- Proper CSS custom properties with semantic names (`--color-background`, `--color-accent-lavender`)
- Grid layout with `repeat(auto-fit, minmax(300px, 1fr))` — responsive without media queries
- Hover effects with `transform: translateY(-8px)` and box-shadow transitions
- Semantic HTML: `<article>` for role cards, `<header>` for hero, `<footer>` for footer
- CSS variables for color theming — easy to modify later
- Proper spacing: `padding: 30px` on cards, `gap: 30px` on grid
- Border-top accent on each role card (4px solid with different colors per role)

**What it got wrong:**

- Hardcoded year in footer (`2024`) instead of dynamic
- No mobile breakpoint for the grid (relies on auto-fit, which works but isn't explicit)
- Hero section has no call-to-action button (just text)
- Role descriptions are generic ("Defines the vision", "Turns plans into action") — not specific to Kufu's actual architecture

**Verdict**: Decent landing page. The CSS is clean, the HTML is semantic, the layout is responsive. A human developer would ship this with some tweaks but the layout would remain mostly the same.

### Single output (run-002-single/single.txt)

**What it got right:**

- Similar structure: hero, roles grid, footer
- CSS custom properties for colors
- Hover effects on cards

**What it got wrong:**

- Cards use `flex: 1` with `max-width: 350px` — on wide screens, cards don't fill the width
- Role descriptions are even more generic than pipeline ("The initial orchestrator", "This model takes the plan")
- Footer has hardcoded year and generic "Built with Open Source Principles"
- No border accents on cards — all cards look identical
- Hero has a button but it's just `onclick="location.href='#roles'"` — no actual CTA text

**Verdict**: Semi-functional but generic. The CSS works but need a LOT of work. The cards look like a template, not a designed component.

### Single with thinking (run-002-single-thinking/single.txt)

**What it got right:**

- Longer output (292 lines vs 232)
- More detailed role descriptions

**What it got wrong:**

- Cards use `flex: 1` with `max-width: 350px` — same problem as single
- Role cards have `border-top: 3px solid` but all use the same color (no differentiation)
- Footer is just "© 2024 Kufu Project" — no links, no social, no personality
- Hero button is `onclick="location.href='#roles'"` — same lazy pattern

**Verdict**: Thinking made the output worse. The model spent tokens on verbose descriptions instead of better CSS. The cards are less visually distinct than the pipeline output making them almost invisible as they blend with the background. The site is NOT aligned to the center, it is on the left side and the site is barely readable.

## Why the pipeline output is better

The pipeline's advantage is not about having extra files — the `requiredFiles` was empty, so the implementer created the page from scratch with zero file references, just like the single runs. The advantage comes from three structural differences:

1. **Planner task as a detailed specification** — the planner's `task` field (87 tokens, 20+ words) acted as a focused, structured brief. The single runs received only the raw user prompt (130 tokens) with no distillation or direction. The planner essentially did a first-pass refinement of the prompt before the implementer touched it.
2. **Implementer has a system prompt** directing it to "Output the complete updated target file. No prose, no markdown fences." The single runs had no system prompt at all — the model defaulted to wrapping output in prose, which degrades code quality.
3. **No thinking on the implementer** — the implementer ran with `think: false`. It produced direct, actionable code. The single run with thinking (which did have the same user prompt) spent tokens on reasoning instead of output quality and produced worse code.

The pipeline planner forced specificity by the `min(20)` constraint. The task field was an 87-token description that gave the implementer a checklist to follow, instead of letting the model guess what the user wanted from a raw prompt.

## Planner thinking vs output mismatch

The planner's thinking trace shows it reasoning about `styles.css`:

> "styles.css exists separately. Since the requirement is a single HTML file with embedded CSS, I should aim to replace or consolidate this content into `<style>` tags within the HTML file, meaning I probably don't need to modify it for the main output, but the structure will heavily use its concepts (design/CSS)."

But the actual JSON output has `"requiredFiles": []` — empty. The planner decided `styles.css` wasn't needed, even though its own thinking said it would be useful.

**Root cause**: The planner's thinking is a stream-of-consciousness trace. The JSON output is a separate generation step. The model doesn't enforce consistency between them. It reasoned "I don't need to modify styles.css" and then output `requiredFiles: []` because it interpreted "required" as "files I must modify" instead of "files the implementer should read."

This is a schema ambiguity problem. The `requiredFiles` field should be documented as "files the implementer needs to read, not necessarily modify." The current description says "Files the implementer must see" which is correct, but the model interpreted it as "files I must change."

## What worked

1. **Schema tightening** — removing `id` and adding `min(20)` to `task` forced the planner to produce actionable instructions.
2. **Planner task as specification** — the planner's descriptive `task` field acted as a structured brief for the implementer, which produced more focused code than the single runs receiving only the raw user prompt.
3. **Pipeline structure** — the two-step process (plan, then implement) produced more specific output than a single prompt.

## What didn't work

1. **Planner thinking consistency** — the planner's reasoning doesn't match its output. This is a model limitation, not a schema problem.
2. **Single with thinking** — enabling thinking on the single run made the output worse, not better. The model spent tokens on verbose descriptions instead of better code.
3. **Token efficiency** — the pipeline uses 8× more input tokens than single. For small models with limited context, this overhead matters.

## Next steps

1. **Clarify `requiredFiles` semantics** — update the schema description to say "files the implementer should read, not necessarily modify."
2. **Test with larger context** — try `num_ctx: 16384` to see if the planner's thinking becomes more consistent with its output.
3. **Add implementer validation** — check that the implementer's output is valid HTML before writing it to disk.
4. **Compare with better models** — run the same prompt with `qwen3:8b` or `llama3.1:8b` to see if the pipeline advantage holds.
