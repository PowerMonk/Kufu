# Run 001 — First engine run

- **Date**: 2026-06-15
- **Model**: `gemma4:e4b` (confirmed via `ollama list`)
- **Context window**: `num_ctx = 8192`
- **Prompt**: `simple-prompt.md`
- **Eval folder**: `eval/` (the three seed files were `index.html`, `readme.md`, `styles.css`)

## What was attempted

Two runs were launched back-to-back against the same prompt:

1. **Pipeline** — the planner was given the file names, the implementer was given
   the files the planner selected, and the engine wrote artifacts to
   `eval/run-001/`.
2. **Single** — the prompt was sent to the model directly with no planning
   step; artifacts went to `eval/run-001-single/`.

The user inspected both runs and reported that the pipeline implementer "did
absolutely nothing" and the implementer's output was byte-identical to the
existing `eval/index.html`. This log records what actually happened, why, and
what we should change next.

## What actually happened — the planner's thinking, parsed

The planner's response had two parts: the JSON it produced, and a long
"thinking" trace inside `planner.json` that explained *how* it produced it.
The thinking reads as the model hedging back and forth between CREATE and
UPDATE without ever committing to what the change is.

Quoting the thinking verbatim (truncated where the file's line length cap
cut it off):

> The user wants to create a landing page for an open-source project called
> "Kufu". This page must be in a single HTML file with embedded CSS.
>
> Available files:
> 1. index.html
> 2. readme.md
> 3. styles.css
>
> Constraints from the request:
> - Single HTML file.
> - Embedded CSS (implies putting `<style>` tags inside `index.html`).
> - Content must cover: Hero section, explanation of 3 system roles
>   (Planner, Implementer, Reviewer), and a footer.
> - Styling requirements: Modern, clean tech design, matte dark mode, soft
>   pastel color palette, no bright colors.
> - Technical requirements: Semantic HTML5, responsive design
>   (Flexbox or Grid).
>
> Since the user explicitly requested a single HTML file *with embedded
> CSS*, and `index.html` is the primary place for an HTML landing page,
> this file should be modified/created to contain all necessary structure
> and styling.
>
> Although `styles.css` exists, the requirement for "a single HTML file
> with embedded CSS" suggests that putting everything into `<style>` tags
> within `index.html` is preferred over linking external sheets. If I
> update `index.html`, I can embed the CSS there.
>
> Plan:
> 1. Set `preferredOutcome` to `index.html`.
> 2. Action must be CREATE or UPDATE. Since we are creating the content,
>    UPDATE seems appropriate if index.html exists, assuming it needs
>    full replacement/modification for this purpose. Given the goal is a
>    complete landing page structure, UPDATE is suitable.
> 3. `requiredFiles`: I only need to modify `index.html`. The other files
>    (`readme.md`, `styles.css`) are not needed for the primary output
>    structure if everything is embedded in `index.html`.
>
> Let's refine the choice: … (file truncated)

The planner correctly identified the conflict between "embed CSS" and the
existing `styles.css` file, but it never resolved the conflict. It picked
UPDATE, asked for the file it was about to overwrite as a `requiredFile`,
and then wrote the action verb into the `task` field.

## What the planner actually returned

```json
{
  "id": "index.html",
  "task": "UPDATE",
  "preferredOutcome": "index.html",
  "requiredFiles": ["styles.css", "index.html"],
  "action": "UPDATE",
  "thinking": "…"
}
```

Two things are wrong on the surface:

1. **`id` is `"index.html"`** — a file path where the schema asked for an
   identifier. The Zod schema in `engine/src/schema.ts` only requires
   `min(1)`, so it let the model get away with it. The model is treating
   `id` as a free-form label.
2. **`task` is `"UPDATE"`** — the action verb, not a description of the
   change. The schema accepts any non-empty string, so this passed. With
   no concrete instruction, the implementer had nothing to do.
3. **`requiredFiles` includes `index.html`** — the file the planner is
   about to UPDATE. The engine's defensive check in `engine/src/planner.ts`
   verifies every required file exists, but it does not (and arguably
   should not) reject "you're about to overwrite a file you also asked to
   read." A human would never do this; the model is just being literal.
4. **`styles.css` is in `requiredFiles` even though the thinking says
   "structurally, it's ignored."** — the model decided it didn't need the
   CSS file, then asked for it anyway. Wasted context for the implementer.

The defensive check in `planner.ts` did its job: it caught that all three
files exist, so the response was passed through. The check is not designed
to catch nonsense; it only catches outright lies about file existence.

## What the implementer did with that

The implementer received:

- The task: "UPDATE"
- The target: `index.html`
- The action: UPDATE
- The file contents: the existing `index.html` and `styles.css`, concatenated

The implementer prompt (see `engine/src/prompts.ts`) said:

> You are the Implementer for Kufu. You will receive a single task and the
> exact files the Planner selected. Assume any file not present in the
> provided context does not exist. Do not request additional files. Output
> the complete updated target file.

The task was literally the word "UPDATE." The implementer produced a file
that was identical to the input, except for a single trivial change: it
turned `<code>` into `<code class="language-json">` in the existing
`<pre><code>{"event": "PIPELINE_COMPLETED", ...}</code></pre>` block. That
is, it made one cosmetic tweak and called it done. From the implementer's
point of view, "I have the file. The task says UPDATE. Here is the
updated file. Done."

The diff between `eval/index.html` (before) and `eval/run-001/implementer.txt`
(after) is exactly one tag attribute. A `git diff` would show one line
changed.

## Why the single run succeeded

The single run sent the same prompt directly to the model with `think: false`.
The model produced a 200-line HTML file with embedded CSS that hit every
section the prompt asked for: a hero, an "agents" section, a footer, soft
pastel palette, matte dark mode, embedded styles. The output was 2,547
tokens, larger than the pipeline's total of 473.

The single run worked because the prompt itself was the only context the
model had. There was no planner, no action-verb `task` field, no
`requiredFiles` indirection. The model just wrote code, which is what it
does well.

## Where the pipeline lost

The pipeline's contract assumes the planner can turn a natural-language
request into a precise, file-level change. On this run the planner:

- Filled `id` with a file path instead of a uuid.
- Filled `task` with the action verb instead of describing the change.
- Asked for the file it was about to overwrite as a `requiredFile`.
- Wasted tokens including `styles.css` in the implementer's context when
  the thinking said it didn't need it.

These four errors are the same error, repeated: the model was lazy with
the schema. It filled the fields with the easiest possible values and
called it done. The Zod schema was permissive enough that all four
"lazy values" passed validation.

## What I'd change next (not done in this commit)

1. **Tighten the Zod schema for `PlannerTask`**:
   - `id`: `z.string().uuid()` or `z.string().regex(/^[a-z0-9-]+$/)` so a
     file path is rejected.
   - `task`: `z.string().min(20)` (or a `.refine` that requires at least
     four whitespace-separated tokens) so a one-word task is rejected.
   - `preferredOutcome` should not be a member of `requiredFiles`. The
     engine can derive that invariant and reject it.
2. **Implementer prompt should explicitly say**: "If the task is just an
   action verb with no concrete change to make, return the file unchanged
   and start the response with the comment `<!-- Kufu: no change
   required, task was a no-op -->`. Do not invent changes." This makes
   the failure mode visible instead of silent.
3. **The planner's defensive check** should reject when
   `preferredOutcome` is in `requiredFiles`. The current engine happily
   passes it through.
4. **Thinking budget**: the planner used 43 seconds to produce 44 output
   tokens. For a model with thinking on, that's the cost of admission.
   Worth measuring whether `num_ctx: 16384` lets the planner think more
   productively or just makes the same lazy decision slower.
5. **Single-run baseline is not actually a fair comparison** for an MVP
   test. The single run had no JSON contract, no schema validation, no
   defensive checks. The pipeline's overhead is real and visible in this
   first run. As we tighten the planner contract and the implementer
   prompt, the pipeline should start paying for itself.

## What I am NOT doing

- I am not changing the schema, the planner prompt, the implementer
  prompt, or the engine code in this commit. The user asked for logs
  and a push, not fixes. The fixes above are recommendations for the
  next iteration.
- I am not re-running the pipeline. The first-run artifacts are
  preserved as-is in `eval/run-001/` and `eval/run-001-single/` so we
  can compare future runs against them.
