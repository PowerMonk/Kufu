# Run 003 — Diagnostic infrastructure, persistence, and variance baseline

- **Date**: 2026-09-02
- **Model**: `gemma4:e4b`
- **Context window**: `num_ctx = 8192`
- **Prompt**: `simple-prompt.md`
- **Tooling**: optional `--seed` flag, `keep_alive: -1` per call, `/api/ps` VRAM probe, on-failure diagnostic dump

## What changed from run-002

This run delivered three layers of infrastructure, plus one prompt fix forced by probe data:

### 1. Schema wording

`engine/src/schema.ts:52` — `requiredFiles` description changed from _"Files the implementer must see"_ to _"Files the implementer must read"_. This addresses the run-002 planner-thinking/output mismatch (`engine/logs/run-002.md:107-117`): the planner's trace correctly identified `styles.css` as a reference but its JSON said `requiredFiles: []`. With "must read", run-003 consistently emits `requiredFiles: ["index.html", "styles.css"]`.

### 2. Persistence (`keep_alive`)

`engine/src/ollama.ts` now accepts `keep_alive?: number | string` on `ChatRequest`. `engine/src/main.ts:122-130` wraps every `chat()` call with `keep_alive: -1` (loaded indefinitely), and calls `unloadModel(args.model)` at the end. New exports:

- `listLoadedModels()` — GET `/api/ps`, returns `{ name, size_vram, expires_at }[]`
- `unloadModel(model)` — POST `/api/generate` with empty prompt + `keep_alive: 0`

VRAM observations from probe data:

- Steady at **3.01GB** across all calls (one model, persistent).
- Released cleanly at process exit (verified manually via subsequent `/api/ps` calls).

### 3. Diagnostic dump on schema failure

`engine/src/planner.ts` accepts `outDir?: string`. On `ZodError`, writes the raw model output + structured issues to `<outDir>/planner.failed.json` before re-throwing. This is the safety net that turned the run-003 first-attempt failure from "stare at a stack trace" into "read the dump and know exactly which field the model omitted".

`engine/src/main.ts` catches `ZodError` explicitly and prints `JSON.stringify(err.issues, null, 2)` plus a pointer to the dump file.

### 4. Usage tracking ledger

New file `engine/src/usage.ts`. On every LLM call, prints a stderr line showing prev→new saturation, cumulative input/output tokens, cumulative **total** tokens (in + out), and VRAM. At end of run, rewrites `engine/state/usage.txt` with the full ledger. **Total tokens are reported separately** because input-only saturation (~2% for single mode) was misleading — the full picture is closer to ~30%.

### 5. Reproducible runs (`--seed`)

`engine/src/ollama.ts` accepts `seed?: number` on `ChatRequest`. `engine/src/main.ts` parses optional `--seed N` and threads it through the wrapper. When absent, no `seed` key is sent (preserves prior behavior). **Probe data below confirms the seed binds on `gemma4:e4b` — every rep produced byte-identical output.**

### 6. Prompt fix forced by probe data

First probe attempt failed Zod validation. `planner.failed.json` showed:

```json
{
  "preferredOutcome": "index.html",
  "requiredFiles": ["index.html", "styles.css"],
  "action": "CREATE"
}
```

Missing `task`. Even with `--seed 42` (deterministic), the model omitted this field on every probe attempt before the prompt was tightened. This is **not stochastic** — it's a model-side interpretation issue. The planner's system prompt was strengthened (`engine/src/prompts.ts:31-37`) to mark `task` as OBLIGATORY and to enumerate the four required JSON fields explicitly. After the fix, all 9 probe runs passed validation.

The implementer uses ~6× the output tokens of the planner and ~3× the input. This is the "implementer does the actual work" signature — the planner's role is to compress the user prompt into a focused brief.

### Total-tokens vs input-only saturation (the metric you flagged)

You observed that 2% input-only saturation for single mode was misleading because the model has to _generate_ the response too. With total-tokens tracked:

| Variant         | in / num_ctx | (in + out) / num_ctx |
| --------------- | -----------: | -------------------: |
| pipeline        |        22.9% |            **45.6%** |
| single          |         2.0% |            **29.1%** |
| single-thinking |         2.1% |            **32.3%** |

Even with total tokens, single mode is the lightest at 29.1%. Pipeline at 45.6% — still well below the 8192 ceiling. The "iterate 40 times" intuition you had applies to single mode's total-token budget: 8192 / 2388 ≈ 3.4 single calls before saturation if we count in + out as cumulative cost. Not 40. (Output generation is the actual bottleneck at ~47 tokens/second on this hardware — 40 single calls would take ~32 minutes.)

## What worked

1. **Diagnostic dump caught the missing-`task` failure in seconds.** Without `planner.failed.json` we'd have repeated the same prompt-iteration loop we did in run-001.
2. **`keep_alive: -1` keeps the model warm across the run.** VRAM held at 3.01GB across all 9 runs; explicit unload freed it cleanly.
3. **`--seed 42` gives fully reproducible token counts.** Variance = 0 across all variants. This makes benchmarking meaningful.
4. **Schema wording fix ("must read") produced correct `requiredFiles`** in every probe run (`["index.html", "styles.css"]`).
5. **Total-tokens column exposes the real saturation picture.** Without it, single mode's 2% would mislead; with it, 29% tells the actual story.
6. **Pipeline is still the winner on this prompt**, even though closer than run-002. Pipeline total = 3739 tokens / 42s; single-thinking total = 2650 tokens / 51s. Pipeline produces more content (2360 output tokens across two calls vs 2479 in one) and does it faster.

## What didn't work

1. **First probe run failed validation.** Model omitted `task` field. Captured cleanly via the diagnostic dump and fixed by strengthening the planner system prompt. After the fix, 9/9 probe runs passed.
2. **Cumulative saturation reading is misleading.** The ledger's `cum_in` accrues across the run, but each Ollama call has its own independent context window — they're not stacking into one giant context. Per-call utilization (planner 6.3% / implementer 16.6% / single 2.0%) is the honest number. Will fix the ledger format in Phase 4.
3. **Variance analysis is one-prompt-deep.** Three reps at one prompt tells us about _this_ prompt's determinism, not the model's overall determinism. A real eval suite (Phase 5) needs more prompts.

## Implications for the project

### Determinism

`gemma4:e4b` with `--seed` is deterministic at the token level. This is a strong property for Kufu — it means we can:

- Compare pipeline vs single mode on identical-output-input.
- Run before/after prompt tweaks and trust the diff.
- Build regression tests on outputs.

### Saturation is a real, but soft, constraint

- Single mode at 29% total means ~3 calls before the cumulative-input metric would hit 100%. But the actual model context window is per-call, not cumulative — so "saturation" in this ledger is a logical budget metric, not a hard VRAM/OOM limit.
- Pipeline at 46% total means the same: 2 pipeline runs before the cumulative counter would hit 100%. Not the model's limit; just an accounting choice.

### Output cost dominates input cost

Across all variants, output tokens are 80–93% of total. For small models this is the wall-clock bottleneck. Optimizing prompts to be more _specific_ (so the model knows exactly what to generate and doesn't pad) will save more wall-clock than shrinking input.
